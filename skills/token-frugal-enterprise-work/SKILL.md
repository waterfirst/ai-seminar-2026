# Token-Frugal Enterprise Work

## 1. 검색부터

저장소의 README, 기존 SQL·Python·HTML, 관련 Skill을 먼저 검색한다. 재사용 가능하면 새로 생성하지 않는다.

## 2. 작업 계약

아래 다섯 항목이 없으면 짧게 확인한다.

- 목적
- 입력 데이터와 위치
- 산출물
- 보안·도구 제약
- 완료 조건

위 항목을 `PLAN.md`에 먼저 기록한다. 계획이 승인되기 전에는 광범위한 파일 수정이나 전체 데이터 처리를 시작하지 않는다.

## 3. 데이터 품질

- YMS·Cubic 등 공식 원천을 식별한다.
- 테이블·컬럼의 의미, 단위, owner, 갱신시점, information label을 기록한다.
- 결측, 중복, 범위, 시간 정렬을 코드로 검사한다.
- 분석 계층은 가능하면 `time / entity / metric / value / unit` long format으로 만든다.
- 실제 사내 데이터와 비밀정보를 프롬프트·Git에 복사하지 않는다.
- Cubic 접속 오류는 SQL 문법과 Python·드라이버 호환 문제를 분리한다. 회사에서 검증된 낮은 Python 버전이 필요한 경우 README에 고정한다.

## 4. 실행

- 파일 전체가 아닌 필요한 조각만 읽는다.
- 회사 환경에서는 MCP를 전제로 하지 않는다. 승인된 로컬 파일, 사내 GitHub, VS Code, Python을 기본으로 한다.
- RTK 같은 외부 실행파일은 승인 전 설치하지 않는다. Python·SQL·검색 범위 제한으로 출력을 줄인다.
- 포맷·변환·집계는 스크립트로 처리한다.
- 고급 모델은 설계, 예외 판단, 최종 검토에만 사용한다.
- 수정 반복은 최대 3회로 제한한다. 같은 오류 2회면 중단한다.

## 5. 산출물

- 판단과 작업 지시는 Markdown에 남긴다.
- 반복 조회 보고서는 HTML을 우선하고 PPT·Word는 승인·대외 보고에 병행한다.
- README에 목적, 입력, 실행법, 검증 결과, 담당자, 재사용 방법을 남긴다.
- GitHub 계정이 없으면 영문 `snake_case` 프로젝트 폴더에 PLAN, README, SKILL, src, raw, output을 함께 보관한다.
- 새 코드가 다른 사람에게 재사용될 수 있으면 공용 저장소나 카탈로그 등록을 제안한다.
